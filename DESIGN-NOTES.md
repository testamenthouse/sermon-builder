# Sermon Builder — design log

## 2026-10-07 — built from scratch in one session (assumptions made, listed here)
- **Base**: Writer (the Writer repo) for look, tokens, dark theme, folder-utility model, autosave + watcher, Letter print rules, Electron shell + updater. Writer's `.dc.html` template runtime was **not** reused: the README there says to recreate the UI in a real stack, so this is Vite + React JSX, plain CSS classes over the same tokens.
- **Sermonary research** (sermonary.com, support articles): blocks = Bible Verse, Point, Illustration, Application, Quote, Custom, Media; per-block Hide-in-Podium and Mark-for-Slide; Podium Mode with countdown clock and font size; templates Three Point, Verse-by-Verse, Me·We·God·You·We, Defender, Children's, Youth 5 C's + Wedding/Funeral/Dedication/Graduation; words + minutes; illustrations library; PDF/Word/slides export. All adopted except Media (links work in Markdown), AI Recap/Insights/Team (not wanted) and sharing (local-only app).
- **Added beyond Sermonary**: transition / conclusion / prayer / invitation / question / note kinds, handout print, tappable in-prose references in Podium, `Dates` library view, series colors, the MCP hook.
- **File format** chosen over JSON so Claude (and a person) can edit sermons as plain text: frontmatter + `::: kind Heading {flags}` fences. Unknown kinds become custom blocks — templates like Me·We·God·You·We rely on this.
- **Storage**: one file per sermon (not a folder) — series = subfolder. `Templates/` and `Illustrations/` reserved. Filename = title slug; title/series changes move the file.
- **Electron file I/O via IPC** (not the File System Access API): the main process must know the library path so the MCP server can read it from `config.json`, and `fs.watch` beats polling. The browser adapter (FSA) exists for the Vite dev server and headless Playwright QA only.
- **KJV**: thiagobodruk/bible `en_kjv.json` (public domain text, Portuguese book names replaced from `shared/books.js`), verified 31,102 verses and chapter counts; bundled as `kjv.json` (4.2 MB) and fetched once.
- **Podium clock** counts down from the sermon's own `length` (Sermon dialog); with none it counts up; ⌥-click resets. Elapsed/remaining toggle like Sermonary's.
- **Word export** is a hand-built docx (store-only zip, five XML parts) — no library, same as Writer's zip.
- **Slides** (Mark-for-Slide + a text export) were removed 2026-10-07: nobody pastes into presentation software, and the media team gets the Verse list PDF instead.
- Receipt printing was removed 2026-10-07: it was Writer's feature only (user). Print is Letter, with optional page numbers.
- Podium rebuilt 2026-10-07 (user: too much margin, too dark, wanted one block presented with the next staged): wide stage, current block centered at full contrast, neighbors at .28 opacity, scroll tracks the nearest block, no fill box. The old `pb` block class collided with the `.pb` primary-button rule and painted every block black; blocks are now `.stage`.
- References dedupe 2026-10-08 (user: `Psalm 1:5, 6, 5` filled verse 5 twice): `parseRef` drops a part an earlier part already covers, and `verses()` never emits the same verse twice, so the block body, the Bible pane and the Verse list all read one place.
- Speaking pace, the ≈ minutes estimate and the global Sermon length default removed 2026-10-07 (user: too complicated); word count stays, the Podium countdown comes only from the per-sermon length.
- Manuscript print redesigned 2026-10-07 (user: far from beautiful): see README Print. KJV data had a space before punctuation after LORD (`LORD .`); normalized in data and in build-kjv.js.
- Outline rail rows 2026-10-07: hover grip + trash (confirm card), drop line between rows while dragging (user: delete must be easy, drag must be obvious).
- Scripture reference refills on change 2026-10-07 (user): `setReference` keeps the raw text while typing and replaces the body whenever the reference resolves to a different passage than before (same passage, or an unresolvable partial, leaves the body alone); blur/Enter still normalize the reference. `Refill KJV` stays for a pasted translation.
- Block menu is a single `…` dropdown with labeled rows (house ruling: crowded icon bars → one dots menu).
- Kind menu (`KindMenu`) is `position: fixed`, anchored to its `+` or caption, flips above when the viewport has more room there, caps its height to the free space and scrolls inside itself (`overscroll-behavior: contain`). An in-flow absolute menu grew the document and focusing its filter scrolled the sermon up (user, 2026-10-07). The filter is focused only after placement because a `visibility: hidden` input refuses focus.

## 2026-10-08 — points are containers
- User: points should be containers that organize the other elements, and sub-points can only live in a point. Agreed; the Outline print already inferred this, the editor just never showed it.
- **File stays flat.** The hierarchy is derived from block order by one rule in `shared/outline.js` (point → next point / transition / closer; sub-point → next sub-point / group end; transitions between groups). A nested fence format would have touched the round-trip contract, every template, the MCP hook and both exports for no gain. If "this block belongs to the sermon, not to point 3" ever bites, an explicit `::: /point` end marker is a small additive change.
- **Transitions sit between groups**, not inside the preceding point — that is what a transition is. The print Outline changed to match (one rule everywhere).
- **Containers behave as containers**: drag, Move up/down, duplicate and delete carry the group; the rail folds them; drop lines snap to group boundaries; a sub-point dropped outside every point is a no-op rather than an orphan. Orphans in files read as points (tolerant parse, documented).
- Numbers moved from the kind caption to the gutter beside the rule (like the manuscript print). Fold state is per session, not persisted — block ids are regenerated on every parse so there is nothing stable to key it on.
- User, same day: a second vertical rule for sub-points was "super horrible" — removed. Sub-point groups are indent + gutter letter only; the point rule alone carries the container.
- User, later: **sub-points removed altogether** ("not great"). One level of structure only. `subpoint` fences read as points so old files keep their content. Tab/Shift-Tab demotion is gone.
- User: adding a Point from inside a point's group split the group and took the rest of the blocks with it. Ruling: **nothing that ends a group is created inside one** — the `+` inside a container omits point, transition and the closing kinds (except at the container's end); those kinds also drag and step only between groups.
- User: **points are first-class constructs** — a point never changes kind and nothing becomes a point; `+` → Point is the only way in. The caption on a point is inert.
- The Question kind had a `?` pseudo-element before the body that rendered as a dead line — removed.

- User: `From library` in a block's `…` menu removed — it only opened the Illustrations pane, whose Insert creates a new block when the current one is filled, so the row meant nothing on an existing block. The pane (⌘I, bulb) is the way in.
- User: "Can each module have its own colors?" — yes: one ink color per kind, applied only to the small structural marks (caption, glyph, number, point rule) so the page stays Writer-quiet; text and print untouched. Ten fixed swatches rather than a free picker, settings-level not per-block, defaults on. Implemented as a `--kc` custom property on each block/row/stage with the faint token as fallback.
- User: colors should print too, and consecutive point rules ran into each other. Print and Word labels/numbers now take the kind color (`print-color-adjust: exact`); the trailing `+` of a group moved outside its rule with 10px of rule past the last block, so two points in a row are visibly two containers.
- User: a printed point should float left of the group it contains. Manuscript and Outline now wrap each point group (`.pg`): number in a 12mm gutter, rule in the point color, the point row unlabeled — the same picture as the editor. Handout stays a flat numbered list.
- User: the print group rule was "GROSSSSS" and he hates vertical point lines everywhere. **No rules anywhere**: editor and rail show the group by indent only (number in the gutter); print opens each point group with a flush-left number + title heading line and indents the group beneath it (the label column does the indenting). Handout unchanged.
- User: some grouping is still wanted — "a faint outline of points". Editor, rail and print now box each point group in a 1px hairline with rounded corners; the number sits inside the box ahead of the caption (editor) or the heading line (print). Still no vertical rules.
- User: no boxes in the left rail. The rail shows a group by indent only; the outline stays in the editor and print.
- User: the gutter number and the caption were out of line. The number is now inline in the caption row (`.pn` before `POINT`), not absolutely positioned.
- User: "Remove all the counts" — per-row word counts dropped from the rail. The only count is the sermon total bottom-right.
- User: rail points should be more prominent and float left of their group. Point rows are now bold, full ink, number flush left, hung 6px left; children indent 28px.

Month headings in Dates and `Templates` / `Unfiled` take the same style so every section reads the same way.

- User, same day: the first list view "feels lame… it all runs together". The list is now a table: column captions, a hairline under every row, fixed Date / Title / Series / Passage / Status columns; the section heading gives up its hairline in list mode so the rules do not double.

## 2026-10-08 — templates are files
- User: "a place to manage templates… a templates folder… dynamic and selectable", "localized to the user's folder". The built-in list in `shared/templates.js` is now only a seed: a library that opens without a `Templates/` folder gets the thirteen starters written as ordinary template files (app and MCP server both seed, so either side can be first); after that the folder is the only source. Deleting a starter stays deleted (seeding keys on the folder, not on the files), so there is no hidden built-in list to fall back on and no two-tier picker.
- The Templates screen is the library chrome (same `.lib` page, find bar, thumbnails / list toggle) rather than the Illustrations rail: a template is a whole sermon file and edits in the sermon editor, so the list only needs to open it. `←` on a template returns to Templates, on a sermon to the library (`closeSermon` reads `meta.template`). Templates no longer show as a section under the series.
- The `Topical` starter lost its prefilled `Point 1/2/3` headings (placeholder rule from 2026-10-07).
- Status `preached` → `done` (user). Old files read `preached` as `done` and are rewritten on their next save; `STATUSES` is the only list.
- The New Sermon dialog's status, tags and length were dropped on create (`createSermon` ignored them); they now land in the file.
- User: "Why can't this just be a dropdown?" — the template list in the New Sermon dialog is now a dropdown: `ui/Select.jsx`, the app's own (no native select), a field-styled button with a chevron and the options in the shared `.pop`. The `.tpl` list styles are gone.
- User: the library's top `+` should make a new series, since every series heading already has a `+` for a sermon. Top `+` → name dialog → `createSeries` (an empty folder, listed at once with its own `+`; reserved and taken names refused). - User: new series forgot the colors, and there was no way to make a sermon outside a series. The top `+` now opens the Series modal in create mode (name + color, `createSeries(name, color)` writes the folder and its `series.json`); `Unfiled` keeps its heading and `+` whenever any series exists, even with nothing in it.
- User: "I don't think I want an unfiled sermon… not series, maybe collection". Every sermon now lives in a collection: the Sermon modal's field is a dropdown of existing collections (never blank), `createSermon` refuses a blank one, `commitMeta` and MCP `update_sermon` keep the old collection if a blank comes in, MCP `create_sermon` requires one. Any `+` for a sermon opens the Collection modal first when no collection exists; the empty library offers only `New collection`. A stray root file (hand-made) still shows under `Unfiled` — the app cannot refuse files — but nothing in the UI creates one. ## 2026-10-08 — dictation
- User: dictate into sermon sections using the Mac's built-in tools; on the web make sure Chrome is used or alert otherwise. Same feature in Writer, same day.
- Native = Speech.framework in a tiny Swift helper (`desktop/dictate/dictate.swift`, compiled by `sync` into `desktop/bin/dictate`, shipped as an extra resource), not Chromium's recognizer: Electron ships no Google speech keys, and Apple's on-device recognition needs no network. The helper is a child process speaking JSON lines; the renderer never touches the microphone itself.
- Segmenting: Apple grows one transcription per request, so the helper commits what it has after 1.5 s of no change (or 50 s) and starts a fresh request — the editor receives sentences, not one ever-changing blob, and long sessions never hit the per-request limit.
- The web build uses Chrome's Web Speech API (cloud) — the user's call to keep the web version Chrome-only; any other browser gets the plain alert card.
- Text goes in through `execCommand('insertText')` at the caret rather than touching the store, so decoration, autosave, undo and the watcher's "typed in the last 2 s" rule all behave as if typed. The caret is followed across blocks (first walk showed words stuck in the starting block — fixed the same session). Partials are previewed in a bottom bar and never inserted.
- QA: Playwright walk with a fake `SpeechRecognition` (both the prefixed and unprefixed names — Chromium 13x exposes both) covering spacing/capitalizing, paragraph commands, caret following, restart after Chrome's own `onend`, stop on close, file content, and the Chrome card; Electron smoke with `DICTATE_BIN` pointed at a fake helper proves the bridge relay. Live microphone runs need a TCC click and were left to a manual run.
- User: the custom block "makes you have the type and the headline the same". A custom block now has two things: a `label` (its caption, edited in place in the caption row, placeholder `Label`) and an optional headline in the usual heading row. File: `::: custom Label | Headline`; `::: Me` still reads as label `Me`, so every existing file and template is unchanged. The custom caption no longer opens the kind menu (it is the label); `Kind…` sits in the block's `…` menu and `/` on an empty body still works. Print, Word, Podium and the rail treat a custom headline like any other heading.
- User, same day: "It says listening but I don't see any words coming through." Live run of the helper showed the cause on the Mac: `kLSRErrorDomain 201 Siri and Dictation are disabled` on every request, swallowed and retried forever. Now a fatal, specific error (`Dictation is off in System Settings`) and the app opens System Settings → Keyboard once. Second finding: run from a terminal, the helper's speech request crashed on TCC because the terminal (the responsible process) has no usage string — fixed by the helper disclaiming responsibility for itself in dev runs. Third: silent failures are now visible — microphone level drives the bar's dot, engine errors and notes show in the bar.
- User again: "I talk but nothing happens" after Dictation was on. Every capture path on the machine (AVAudioEngine, AVCaptureSession, ffmpeg) returned digital silence: the MacBook was in clamshell mode on an external display, which disables the built-in microphone, the only input device present. Not a code problem — but the helper now says `Microphone is silent` after 3 s of zeros, and gives up with a clear error when speech-level audio produces no result, so neither case is a silent "Listening" again.
- User: saying `period`, `comma`, `exclamation point` added nothing in either app (new paragraphs worked). Cause: only `new paragraph` / `new line` were command words; Chrome's desktop engine and Speech.framework leave the rest as literal words (Apple's `addsPunctuation` is automatic only, and does nothing for a spoken command). Now `spokenPunctuation` maps the macOS Dictation command vocabulary to marks before a segment is joined (attached to the word before, capital after a sentence end, no doubling of a mark the recognizer or the paragraph already has); the partial preview shows the marks too. Same code in Writer's `Dictation.spoken`.
- User: the mic is too hidden while recording; wants a button bottom right to stop. Added a solid `Stop` button bottom right whenever dictation is on (word count slides left of it); the hover-revealed mic in the tools strip remains the way to start.

## 2026-10-08 — no build: browser-friendly out of the box
- User: "Why does it need Vite?" → "I want this to be browser friendly as well out of the box." Vite was my assumption on day one (JSX + many modules), not a requirement. Now the repo folder *is* the web app: `index.html` at the root, an import map pointing `react` / `react-dom/client` / `htm` at `vendor/` (esm.sh ES-module builds with their imports rewired to each other by `scripts/vendor.js`), and every component rewritten from JSX to `htm` templates (`app/src/lib/html.js`; mechanical AST conversion, every non-JSX byte kept). `app/public` folded into `app/`; the KJV is fetched at `data/kjv/kjv.json`. `npm run dev` is a small static server; the Mac shell's `sync` copies the folder instead of building, with the import map allowed by sha256 in the CSP. Vite, the React npm packages and the build step in CI are gone. Verified: Electron smoke under the CSP, a headless Chrome walk (gate → seeded library → sermon, Bible pane, find, print menu, podium, dictation with a spoken period, templates) with zero console errors, `npm test`.
- Ruling: the web build and the Mac app serve the same files; never reintroduce a bundler or a compile step for the UI.

## 2026-10-08 — Chrome only on the web (whole app, not just dictation)
- User: if the browser is not Chrome, they cannot use the app (same in Writer).
